1. ภาพรวมงานแต่ละส่วน

ระบบดึงข้อมูลการจราจรของกรุงเทพฯ จาก 3 แหล่งที่ไม่ต้องใช้ API key ทุก 15 นาที รวมเป็นชุดข้อมูลเดียวด้วย Apache Airflow DAG เก็บใน PostgreSQL และแสดงผลบนเว็บ dashboard (Streamlit) ที่อ่านจาก PostgreSQL โดยตรง ทุกแหล่งถูกแปลงเป็น schema เดียวกันในตาราง traffic_record (source, source_id, record_type, category, title, area, period, event_time, lat, lon, congestion_pct, speed_kmh, free_flow_kmh, severity, dedup_key)

แหล่งวิธีดึงข้อมูลที่ได้
TomTom Traffic IndexWeb scraping ด้วย requests อ่าน JSON ที่ฝังใน HTML (ไม่ใช้ Selenium)ระดับรถติด (%) และความเร็วของกรุงเทพฯ รายชั่วโมงทั้งสัปดาห์ (168 ค่า), รายเดือน, ช่วงเร่งด่วน
Longdo TrafficJSON feed (ทำตาม Crawl-delay: 10)เหตุการณ์จราจร เช่น อุบัติเหตุ น้ำท่วม (กรองเฉพาะกรุงเทพฯ)
Traffy FonduePublic APIเรื่องร้องเรียนของ กทม. เฉพาะหมวดจราจร ถนน น้ำท่วม สะพาน

ทุกแหล่งตรวจ robots.txt ด้วย urllib.robotparser ก่อนดึง · PDPA: ไม่เก็บชื่อผู้รายงาน ข้อความร้องเรียน และรูปภาพ

ระดับสิ่งที่ทำได้ผล
1 ขั้นต่ำDAG extract → transform → load → PostgreSQL → เว็บแสดงตารางและกราฟครบ
2 มาตรฐาน3 แหล่งรันขนานใน TaskGroup extract · รวมเป็น schema เดียว · UPSERT ON CONFLICT (source, source_id) (Clear แล้วรันซ้ำ log ขึ้น "ใหม่ 0") · เว็บมี KPI 3 ตัวและตัวกรอง (ขอบเขต TomTom, วัน, แหล่ง, ช่วงวัน, ประเภท, คำค้น)ครบ
3 ท้าทายแหล่งล่ม: transform ใช้ trigger_rule="all_done" รวมจากแหล่งที่เหลือได้ (สถานะ PARTIAL) · ตัดรายการซ้ำข้ามแหล่ง: เหตุการณ์ Longdo/Traffy กลุ่มเดียวกัน วันเดียวกัน ห่างกัน ≤ ~300 ม. รวมเหลือ 1 แถวในตาราง traffic_event · ตรวจคุณภาพแล้วแตกเส้นทาง: ค่าว่าง ช่วงค่า พิกัดต้องอยู่ในกรุงเทพฯ เวลาไม่อยู่ในอนาคต แล้ว @task.branch ไป load หรือ quarantineครบ
โบนัสหน้า "Pipeline Status" บนเว็บ แสดงสถานะแต่ละแหล่ง ประวัติการรัน และแถวที่ไม่ผ่านการตรวจครบ

จำนวนข้อมูล: เกิน 100 รายการตั้งแต่รอบแรก เพราะ TomTom อย่างเดียวให้ 184 ค่าต่อขอบเขต (รายชั่วโมง 168 + รายเดือน 12 + ช่วงเร่งด่วน 4) รวมกับเหตุการณ์จาก Longdo และ Traffy ตรวจได้ด้วย SELECT COUNT(*) FROM traffic_record · ทุกรอบที่รันบนเครื่องผู้จัดทำ ทั้ง 3 แหล่งเป็น success (ภาพที่ 1–2)

2. ปัญหาที่พบและวิธีแก้

ปัญหา 1: แหล่งข้อมูลที่วางแผนไว้ (Waze Live Map) ดึงไม่ได้ และ robots.txt ไม่อนุญาต

อาการ: task extract.waze ล้มเหลวด้วย HTTP 403 Forbidden

วิธีหาสาเหตุ: เขียนสคริปต์ PowerShell ทดสอบทุก URL ที่วางแผนไว้พร้อมอ่าน robots.txt พบว่า Waze มี Disallow: /live-map/api ส่วน TomTom/HERE Routing API ต้องใช้ key ซึ่งห้าม commit ทำให้อาจารย์รันจาก repo แล้วจะไม่ได้ข้อมูล

วิธีแก้: ทดสอบหาแหล่งที่ไม่ต้องใช้ key และ robots.txt อนุญาต ได้ TomTom Traffic Index (scrape HTML), Longdo feed และ Traffy API แล้วนำตัวอย่างข้อมูลจริงจากการทดสอบมาเขียน unit test ก่อนแก้โค้ด

ปัญหา 2: heatmap บนเว็บขึ้น ValueError: Index contains duplicate entries, cannot reshape

อาการ: ตอนทดสอบด้วยข้อมูลตัวอย่างแสดงผลได้ แต่พอใช้ข้อมูลจริงกราฟ "รถติดช่วงไหนของสัปดาห์" พัง

วิธีหาสาเหตุ: traceback ชี้ไปที่ DataFrame.pivot() จึง query ข้อมูลดู พบว่าหน้า TomTom จริงมีข้อมูลหลายขอบเขต (เช่น metro/city) ทำให้วัน/ชั่วโมงเดียวกันมีหลายค่า ซึ่งข้อมูลตัวอย่างมีขอบเขตเดียวจึงไม่เจอ

วิธีแก้: แยกขอบเขตจาก source_id แล้วเพิ่มตัวเลือก "ขอบเขตข้อมูล TomTom" ให้กรองก่อนวาด และเปลี่ยนเป็น pivot_table

ปัญหา 3: แผนที่บน dashboard ขึ้นลายน้ำ "API KEY REQUIRED"

อาการ: จุดเหตุการณ์แสดงได้ แต่พื้นแผนที่เป็นลายน้ำ carto.com/basemaps/apikey

วิธีหาสาเหตุ: สไตล์ carto-positron ของ plotly ดึงภาพจาก CARTO ซึ่งเปลี่ยนนโยบายให้ต้องใช้ API key แล้ว ยืนยันโดยดักดู request ของเบราว์เซอร์ว่าภาพแผนที่โหลดจาก host ไหน

วิธีแก้: กำหนดแหล่งภาพแผนที่เป็น OpenStreetMap (tile.openstreetmap.org) ผ่าน mapbox_layers ซึ่งไม่ต้องใช้ key

ปัญหา 4: ข้อมูล Traffy มีเรื่องที่ไม่เกี่ยวกับการจราจรปนมา (เช่น เรื่องขยะ)

อาการ / สาเหตุ: เมื่อเรื่องไม่มีประเภท ระบบกรองด้วยคำว่า "ถนน" ในข้อความ แต่ข้อความของ Traffy มีบรรทัด ถนน: <ชื่อถนน> ระบุที่อยู่แทบทุกเรื่อง

วิธีแก้: เลิกใช้คำว่า "ถนน" ใช้เฉพาะ "รถติด/การจราจร/น้ำท่วม" และเพิ่มข้อมูลจริงที่มีบรรทัดนี้ลง unit test กันไม่ให้บั๊กกลับมา
